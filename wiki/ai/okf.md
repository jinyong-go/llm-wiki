## 1. 개요

OKF(Open Knowledge Format)는 데이터와 시스템에 관한 지식을 기록하고 교환하는 형식이다. 각 개념 문서는 YAML 머리말 메타데이터(frontmatter)와 마크다운 본문으로 구성한다. 사람과 AI 에이전트가 읽고 작성할 수 있으며, 전용 도구나 중앙 스키마 레지스트리가 필요하지 않다.

현재 명세 버전은 0.2다. OKF는 개념의 출처, 생성·검증 상태, 최신성 정보를 기록한다. 정해진 방식으로 계산한 값이 그 정의에 맞는지도 확인할 수 있다. 저장·제공·검색 인프라나 고정된 개념 분류 체계는 규정하지 않는다.

## 2. 번들 구조와 용어

지식 번들(knowledge bundle)은 함께 배포하는 계층형 지식 문서 모음이다. 도메인에 맞게 디렉터리를 구성하며, Git 저장소, tarball·zip 파일 또는 더 큰 저장소의 하위 디렉터리로 배포할 수 있다. Git 저장소는 변경 이력과 기여자 정보를 제공하므로 권장된다.

```text
path/to/bundle/
├── index.md          # 선택. 디렉터리 목록
├── log.md            # 선택. 변경 이력
├── <concept>.md      # 번들 루트의 개념 문서
└── <subdirectory>/   # 개념을 그룹화하는 하위 디렉터리
    ├── index.md
    ├── <concept>.md
    └── <subdirectory>/
```

개념(concept)은 번들 안의 지식 단위 하나를 뜻하며, 마크다운 문서 하나로 표현한다. 테이블이나 API 같은 자산과 지표나 업무 절차 같은 추상적인 대상도 나타낼 수 있다. 개념 ID는 번들 안 문서 경로에서 `.md`를 뺀 값이다. 예를 들어 `tables/users.md`의 ID는 `tables/users`다.

`index.md`와 `log.md`는 디렉터리 어디에서나 정해진 용도로 쓰는 예약 파일명이다. 그 밖의 `.md` 파일은 개념 문서다. 태그별 목록을 저장하는 파일 형식은 따로 정하지 않는다. 필요하면 머리말 메타데이터를 읽어 목록을 만들 수 있다.

## 3. 개념 문서

개념 문서는 UTF-8 마크다운 파일이다. 파일 맨 위에 YAML 머리말 메타데이터를 두고, 앞뒤를 `---`로 구분한다. 그 아래에 본문을 작성한다.

### 3.1. Frontmatter

```yaml
---
type: <Type name>              # 필수
title: <표시 이름>              # 선택
description: <한 줄 요약>       # 선택
resource: <자산 정규 URI>      # 선택
tags: [<tag>, <tag>, …]        # 선택
status: <draft|stable|deprecated> # 선택
generated: { by: <actor>, at: <ISO 8601 datetime> } # 선택
verified: [{ by: <actor>, at: <ISO 8601 datetime> }] # 선택
stale_after: <ISO 8601 datetime> # 선택
sources:                       # 선택
  - id: <stable identifier>
    resource: <URI or bundle path>
# … 생산자가 정의하는 추가 키
---
```

`type`은 개념의 종류를 나타내며 필수다. 예를 들어 `BigQuery Table`, `API Endpoint`, `Metric`을 쓸 수 있다. 유형을 중앙에서 관리하지 않으므로 문서 작성자가 의미를 알기 쉬운 값을 정한다. 문서를 읽는 도구는 알 수 없는 유형도 일반 개념으로 처리해야 한다.

`title`, `description`, `resource`, `tags`는 선택 항목이다. `title`이 없으면 파일명으로 표시 이름을 만들 수 있다. `resource`는 개념이 설명하는 자산의 URI다. 추상 개념에는 이 값이 없을 수 있다.

문서 작성자는 머리말 메타데이터에 필드를 추가할 수 있다. 문서를 읽는 도구는 모르는 필드가 있어도 문서를 거부해서는 안 된다. 문서를 다시 저장할 때는 해당 필드를 보존하는 것이 좋다.

### 3.2. 본문

본문은 표준 마크다운으로 작성한다. 필수 섹션은 없지만 다음 제목은 관례적인 용도로 쓰인다.

| 제목 | 용도 |
|---|---|
| `# Schema` | 자산의 열이나 필드 설명 |
| `# Examples` | 사용 예시 |
| `# Computation` | 계산 증명 개념의 계산 정의 |

각주로 본문의 주장을 출처와 연결할 수 있다. 각주 이름에는 `sources` 항목의 `id`를 사용한다.

## 4. 출처와 신뢰 정보

### 4.1. 출처

`sources`에는 개념의 근거가 된 자료를 기록한다. 각 출처 항목에는 `resource`가 필요하다. 절대 URL, 번들 내부 경로 또는 자료의 범위를 설명하는 문자열을 쓸 수 있다. 본문 각주와 연결하려면 항목에 변하지 않는 `id`를 지정한다. 제목도 덧붙일 수 있다.

`author`, `usage_count`, `last_modified`는 출처를 판단할 때 참고하는 정보다. `usage_count`를 기록하면 집계 기간을 `usage_window`에 함께 적을 수 있다. 이 값들은 신뢰 점수가 아니다.

### 4.2. 생성과 검증

`generated`에는 현재 내용을 만든 주체와 시각을 기록한다. `verified`에는 내용을 출처나 대상 자산과 대조해 확인한 주체와 시각을 기록한다. 시각은 시간대가 포함된 ISO 8601 형식으로 쓴다.

주체 식별자는 에이전트와 도구에는 `<producer>/<version>`, 사람에는 `human:<id>`, 자동화 프로세스에는 `process:<id>` 형식을 쓴다. `verified`에 `human:`으로 시작하는 주체가 있으면 사람 검토 상태다. 검증 기록은 있지만 사람 검토자가 없으면 기계 확인 상태다. `verified`가 없으면 미검증 상태다. 이 구분은 접근 제어가 아니라 참고 정보다.

### 4.3. 수명주기와 최신성

`status`에는 `draft`, `stable`, `deprecated` 중 하나를 쓴다. `draft`는 아직 검토 중인 상태, `stable`은 사용할 수 있는 상태, `deprecated`는 더 이상 최신 정보는 아니지만 기록을 위해 남긴 상태다. 생략하면 `stable`로 취급한다. `stale_after`는 내용이 오래된 것으로 판단할 시각이다. 현재 시각이 이 값과 같거나 이후이면 해당 개념은 오래된 상태다.

## 5. 링크와 보조 파일

### 5.1. 개념 간 링크

개념은 표준 마크다운 링크로 연결한다. 번들 루트 기준 링크는 `/tables/customers.md`처럼 `/`로 시작한다. 링크를 적은 문서를 옮겨도 대상 경로가 바뀌지 않으므로 이 방식을 권장한다. 상대 링크는 `./other.md`처럼 쓴다.

링크는 두 개념 사이의 관계를 나타낸다. 부모·자식, 참조, 의존 중 어떤 관계인지는 링크 주변의 문장으로 설명한다. 링크 대상이 아직 없을 수 있으므로 문서를 읽는 도구는 끊어진 링크를 이유로 번들을 거부해서는 안 된다.

### 5.2. `index.md`

`index.md`는 디렉터리의 내용을 섹션별 링크 목록으로 보여 준다. 기본적으로 머리말 메타데이터를 두지 않는다. 번들 루트의 `index.md`에는 `okf_version`을 선언할 수 있다. 목록에는 연결된 개념의 `description`을 포함하는 것이 좋다. 작성 도구는 인덱스를 자동 생성할 수 있고, 읽는 도구는 인덱스가 없을 때 목록을 만들 수 있다.

### 5.3. `log.md`

`log.md`에는 해당 디렉터리의 변경 이력을 기록한다. 날짜 제목은 `YYYY-MM-DD` 형식으로 쓰고 최신 항목부터 배치한다. 각 항목은 산문으로 작성한다. `Update`, `Creation`, `Deprecation` 같은 분류 표시는 관례이며 필수는 아니다.

## 6. 계산 증명

`Attested Computation`은 정해진 입력과 계산 정의로 값을 만들고, 실행 결과가 정의에 맞는지 확인하기 위한 개념 유형이다. 짧은 계산은 본문의 `# Computation` 아래에 둔다. 긴 계산이나 다른 도구와 공유할 계산은 `computation` 경로로 가리킬 수 있다.

`runtime`은 계산 환경을 지정한다. `parameters`는 실행에 필요한 입력을 선언한다. `executor`는 계산 실행 지침이나 코드를 가리키며, `receipt`는 실행 결과에 포함할 항목을 정한다. `attester`는 실행 결과를 결정적으로 확인하는 코드를 가리킨다.

읽는 도구는 선언된 매개변수에 값을 넣어 계산을 실행하고 결과를 검증할 수 있다. `verified`는 계산 정의가 정책이나 출처와 일치하는지 확인한 기록이다. 실행 증명(attestation)은 각 실행 결과가 정해진 계산으로 생성됐는지 확인한다. OKF는 확인에 필요한 정보를 정의하지만, 계산 실행이나 결과 전달을 위한 전체 프로토콜은 정하지 않는다.

## 7. 적합성과 버전

OKF v0.2에 적합한 번들은 예약 파일이 아닌 모든 마크다운 문서에 읽을 수 있는 YAML 머리말 메타데이터와 비어 있지 않은 `type`을 포함한다. `index.md`나 `log.md`가 있으면 각 파일의 구조 규칙을 따른다.

출처, 신뢰도, 수명주기, 계산 필드는 명세의 사용 규칙을 따르는 것이 좋다. 읽는 도구는 선택 필드의 누락, 알 수 없는 `type`이나 추가 필드, 끊어진 링크, `index.md`의 부재를 이유로 번들을 거부해서는 안 된다. `verified`가 목록이 아닌 단일 항목으로 작성되어도 목록의 한 항목으로 처리해야 한다.

OKF 버전은 `<major>.<minor>` 형식이다. 마이너 버전은 이전 버전과 호환되는 필드나 관례적 섹션을 추가한다. 메이저 버전은 필수 필드나 예약 파일명을 바꿀 수 있다. 번들은 루트 `index.md`의 머리말 메타데이터에 `okf_version: "0.2"`를 선언할 수 있다. 읽는 도구가 해당 버전을 몰라도 번들을 거부하지 말고 가능한 범위에서 읽어야 한다.
