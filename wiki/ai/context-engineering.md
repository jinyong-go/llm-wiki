## 1. 개요

컨텍스트(context)는 모델이 응답을 만들 때 참고하도록 전달받는 정보다. 사용자의 요청뿐 아니라 지침, 대화 이력, 검색 결과, 도구 정보와 이전 도구 실행 결과도 포함될 수 있다. 이 정보는 모델이 처리하는 작은 단위인 토큰(token)으로 표현된다.

컨텍스트 엔지니어링(context engineering)은 작업에 필요한 정보를 골라 적절한 시점과 형태로 모델에 제공하고, 작업이 이어지는 동안 이를 관리하는 일이다. Anthropic은 이를 원하는 결과를 얻을 수 있도록 유용한 정보를 선별해 모델에 전달하는 문제로 설명한다.[^1]

모델이 처리할 수 있는 입력 길이에는 한도가 있다. 그러나 한도 안에 정보를 많이 넣는다고 결과가 항상 좋아지는 것은 아니다. 모델과 작업에 따라 긴 입력에서 필요한 정보를 찾거나 여러 정보 사이의 관계를 파악하는 성능이 달라질 수 있다.[^2] 따라서 컨텍스트는 필요한 정보를 충분히 담되, 관련 없는 정보와 불필요한 반복은 줄여야 한다.

## 2. 프롬프트 엔지니어링과의 관계

프롬프트 엔지니어링(prompt engineering)은 모델에 전달할 지시문을 작성하고 다듬는 일이다. 컨텍스트 엔지니어링은 지시문을 포함해 모델이 참고할 정보 전체를 구성하고 관리한다.

두 분야는 서로 대체하는 개념이 아니다. 지시문을 잘 작성하는 일은 컨텍스트를 설계하는 한 부분이다. 한 번의 모델 호출에서도 검색 결과나 출력 형식 같은 정보를 함께 제공한다면 컨텍스트 구성 문제가 생긴다. 반대로 여러 차례 이어지는 대화에서는 새 요청과 이전 대화, 도구 결과 중 무엇을 다음 호출에 포함할지도 결정해야 한다.

## 3. 구성 요소

모델에 제공하는 컨텍스트는 작업에 따라 달라지지만, 일반적으로 다음 정보를 포함할 수 있다.

- **지침**은 모델의 목표, 역할, 제약 조건과 기대하는 응답 형식을 설명한다.
- **사용자 요청**은 현재 해결할 질문이나 작업을 전달한다.
- **대화 상태**는 이전 대화와 도구 실행 결과 중 현재 작업에 필요한 부분을 제공한다.
- **외부 정보**는 문서, 데이터베이스, 웹 등에서 검색한 자료다. 검색 증강 생성(RAG, Retrieval-Augmented Generation)은 외부 정보를 찾아 모델의 입력에 포함하는 대표적인 방식이다.
- **도구 정보**는 모델이 사용할 수 있는 기능과 각 기능에 필요한 입력을 설명한다.
- **응답 형식**은 모델의 결과가 따라야 할 구조나 제약을 지정한다.

이 정보는 모델이 처리할 수 있는 입력 공간을 함께 사용한다. 따라서 긴 대화 이력이나 불필요한 도구 설명을 계속 포함하면 현재 요청에 필요한 정보가 묻히거나 입력 한도에 가까워질 수 있다.

## 4. 컨텍스트가 길어질 때 생기는 문제

컨텍스트가 길어져도 모델이 모든 정보를 같은 정확도로 활용한다고 보장할 수 없다. 긴 입력에서 성능이 달라지는 양상은 모델과 작업, 정보의 관련성에 따라 다르다. 필요한 정보가 입력 안에 있더라도 모델이 이를 놓치거나, 관련 없는 내용에 영향을 받을 수 있다.[^2]

긴 컨텍스트에서 나타날 수 있는 실패를 Drew Breunig는 다음 네 가지로 분류한다.[^3] 이는 설명을 위한 분류이며, 모든 실패가 반드시 이 범주 중 하나에만 속하는 것은 아니다.

| 유형 | 설명 |
| :--- | :--- |
| 오염 | 잘못된 정보가 대화 이력이나 요약에 들어가 이후 판단에 반복해서 영향을 주는 경우 |
| 산만 | 이전 대화나 불필요한 정보가 많아 현재 작업에 집중하기 어려워지는 경우 |
| 혼동 | 관련 없는 정보나 도구가 포함되어 잘못된 정보나 기능을 선택하는 경우 |
| 충돌 | 컨텍스트 안의 지침이나 사실이 서로 모순되는 경우 |

에이전트처럼 여러 단계에 걸쳐 정보를 모으고 도구를 사용하는 시스템에서는 대화 이력과 실행 결과가 계속 쌓인다. 그러므로 새 정보를 추가하는 것뿐 아니라, 이미 전달한 정보를 유지할지 갱신할지도 관리해야 한다.

## 5. 관리 전략

컨텍스트 관리 전략은 서로 배타적인 선택지가 아니다. 작업의 길이와 정보의 종류에 따라 저장, 검색, 압축, 분리를 함께 사용할 수 있다. LangChain은 이를 쓰기(write), 선택(select), 압축(compress), 격리(isolate) 전략으로 묶어 설명한다.[^4]

### 5.1. 저장

나중에 다시 사용할 정보를 모델 입력 바깥의 저장소에 기록한다. 현재 작업의 진행 상황이나 결정 사항을 메모로 남기면 대화가 요약되거나 다시 시작될 때 이어서 작업하는 데 도움이 된다. 여러 세션에서 반복해서 쓸 정보도 별도로 저장할 수 있다.

모든 정보를 저장할 필요는 없다. 오래되었거나 부정확한 정보가 계속 남으면 이후 응답을 오도할 수 있으므로, 무엇을 저장하고 언제 갱신하거나 삭제할지 정한다.

### 5.2. 선택

저장된 정보나 외부 자료 중 현재 요청과 관련 있는 것만 찾아 모델에 전달한다. 문서 검색, 데이터베이스 조회, 파일 이름과 내용 검색 등을 이용할 수 있다. 정보가 많다면 검색 결과를 다시 관련도에 따라 정렬할 수도 있다.

필요한 정보를 미리 찾아 입력에 포함하면 응답이 빠르지만, 검색 결과가 오래되었거나 현재 요청과 맞지 않을 수 있다. 작업 중 파일이나 자료를 찾아 읽는 방식은 필요한 정보만 전달할 수 있지만 탐색 시간이 더 걸린다. 작업에 따라 두 방식을 함께 쓸 수 있다.

### 5.3. 압축

긴 대화나 도구 결과에서 현재 작업에 필요한 핵심을 요약하거나, 이미 처리한 정보를 제거한다. 요약은 결정 사항과 남은 작업을 새 컨텍스트에 이어 전달할 때 쓸 수 있고, 정리는 더 이상 필요하지 않은 이전 메시지나 결과를 제외할 때 쓸 수 있다.

압축 과정에서 중요한 조건이나 예외가 사라질 수 있다. 따라서 원문이나 출처를 다시 확인할 수 있는 참조를 남기고, 요약이 핵심 정보를 보존하는지 대표 작업으로 점검한다.

### 5.4. 분리

큰 작업을 독립적인 하위 작업으로 나누고, 각 작업에 필요한 정보만 따로 제공한다. 각 작업의 결과를 요약해 모으면 전체 컨텍스트에 세부 정보를 모두 넣지 않아도 된다.

분리는 하위 작업이 서로 독립적일 때 효과적이다. 여러 작업을 나누고 결과를 합치는 비용이 들며, 하위 작업 사이에 공유해야 할 정보가 빠질 수도 있다. 따라서 작업 분리로 얻는 이점이 조정 비용보다 큰지 확인한다.

## 6. 적용과 평가

컨텍스트를 설계할 때는 현재 작업에 꼭 필요한 정보와 없어도 되는 정보를 구분한다. 지침, 외부 자료, 대화 이력과 도구 결과를 모두 무조건 포함하지 말고, 각 정보가 어떤 판단에 필요한지 확인한다.

컨텍스트 구성이 실제로 도움이 되는지는 대표 입력과 예상 결과를 모아 평가한다. 예를 들어 필요한 정보를 찾았는지, 잘못된 자료를 근거로 삼았는지, 결과 형식이 요구사항을 따랐는지를 확인할 수 있다. 변경 전후의 결과와 입력 길이를 함께 기록하면 정보 추가나 요약이 품질과 비용에 미친 영향을 비교하기 쉽다.

초기에는 필요한 정보를 충분히 제공하고, 실제 실패 사례를 살펴 불필요하거나 잘못된 정보를 줄인다. 요약·검색·분리 같은 전략도 도입 전후 결과를 비교해 작업 성능이 개선될 때 사용한다.

## 7. 주의 사항

### 7.1. 정보의 정확성과 최신성

잘못된 정보가 대화 이력이나 메모리에 들어가면 이후 단계에서도 반복해서 사용될 수 있다. 검색 자료의 출처와 날짜를 확인하고, 서로 다른 자료가 모순되면 차이를 모델에 명시하거나 추가 검증을 수행한다.

### 7.2. 외부 입력과 지침의 구분

검색한 문서나 웹 페이지에는 모델의 지침을 바꾸려는 문장이 포함될 수 있다. 외부 자료는 작업을 위한 정보로 취급하고, 시스템이 정한 지침이나 권한을 대신하는 명령으로 받아들이지 않도록 설계한다. 특히 외부 자료를 읽은 뒤 도구를 실행하는 작업은 실행 권한과 결과를 별도로 확인한다.

### 7.3. 개인정보와 보관

현재 작업에 필요하지 않은 개인정보나 비밀 정보를 모델에 전달하거나 장기 저장하지 않는다. 메모리를 사용하는 경우 저장 대상, 접근 권한, 보관 기간, 삭제 방법을 정한다. 대화 기록과 실행 기록에도 민감 정보가 남을 수 있으므로 같은 기준으로 관리한다.
